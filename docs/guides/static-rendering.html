Static rendering for SEO

The swiftui-for-web/server entry renders the same views to HTML with no browser, so crawlers and link previews see the page without running JavaScript.

The server entry runs the framework’s own renderers against a small DOM-like shim (src/Server/DOMShim.js). There is no second HTML implementation to keep in sync: the markup is what the browser renderer produces on its first render. Import views from swiftui-for-web as usual, and the server functions from swiftui-for-web/server.

renderToString

renderToString(view) takes a view, a view descriptor or a function returning one, and returns the markup of its first render.

import { VStack, Text, Font, Color } from 'swiftui-for-web';
import { renderToString } from 'swiftui-for-web/server';

const Greeting = (name) =>
  VStack({ alignment: 'leading', spacing: 4 },
    Text(`Hello, ${name}`).font(Font.title),
    Text('Rendered without a browser').foregroundColor(Color.secondary)
  );

// In Node, write the string to a file or a response. In the Playground,
// the default export is shown next to the preview.
export default renderToString(Greeting('Ada'));

What a static render does and doesn’t do:

  • The output is deterministic: the same input gives byte-identical HTML. Attributes and styles keep their order, and generated ARIA ids restart for each render.
  • Effects, animation frames and timers never run, and there is no layout: sizes are 0. Views that wait for a frame or a ResizeObserver (GeometryReader, ViewThatFits) render empty until the client mounts. Lazy stacks render every row.
  • The shim is installed as globals only for the duration of the call and restored afterwards, so importing the framework in Node never touches window or document.
  • It runs where there is no real window: Node, or a Worker. In a browser window it throws, because a window’s own window and document can’t be replaced. (The Playground runs code that imports the server entry in a Worker for this reason.)

renderDocument and DocumentMetadata

renderDocument(view, options) returns a whole document: a <head> with charset, viewport and the scene’s metadata, and a <body> whose root element holds the view’s markup for the client app to mount into. Metadata comes from options.metadata or from a WindowGroup({ metadata }).

import { WindowGroup, VStack, Text, Font } from 'swiftui-for-web';
import { renderDocument, DocumentMetadata } from 'swiftui-for-web/server';

const metadata = new DocumentMetadata({
  title: 'Trail Guide',
  description: 'Hikes near you, with maps and elevation.',
  canonical: 'https://example.com/',
  robots: 'index, follow',
  openGraph: { type: 'website', image: 'https://example.com/og.png', imageAlt: 'A mountain trail' },
  twitter: { card: 'summary_large_image' },
  jsonLD: { '@context': 'https://schema.org', '@type': 'WebSite', name: 'Trail Guide' },
});

export default renderDocument(
  WindowGroup({ metadata }, () =>
    VStack({ spacing: 8 },
      Text('Trail Guide').font(Font.largeTitle).accessibilityHeading('h1'),
      Text('Twelve hikes within an hour of the city.')
    )
  ),
  { stylesheets: ['/styles/index.css'], scripts: ['/main.js'] }
);
OptionDefaultMeaning

DocumentMetadata fields: title, description, canonical, robots, openGraph (title, description, type, url, image, imageAlt, siteName, locale), twitter (card, site, creator) and jsonLD. A missing title comes from the view’s .navigationTitle(_:), then from the WindowGroup’s title.

Every value is escaped. URLs (canonical, Open Graph) must be http(s), robots directives are checked, and JSON-LD is serialized so it can’t close its <script> element. DocumentMetadata is a web-only API: SwiftUI has no document head.

sitemap

sitemap(routes, { baseURL }) writes sitemaps.org XML. A route is a path, or an object with path (or url), lastModified, changeFrequency and priority.

import { sitemap } from 'swiftui-for-web/server';

export default sitemap([
  '/',
  { path: '/trails', changeFrequency: 'weekly', priority: 0.8 },
  { path: '/about', lastModified: '2026-11-01' },
], { baseURL: 'https://example.com' });

A prerender script

In a project, a small Node script writes the pages at deploy time. The client then hydrates the markup with mode: 'adopt'.

// prerender.mjs: node prerender.mjs
import { mkdir, writeFile } from 'node:fs/promises';
import { WindowGroup, VStack, Text } from 'swiftui-for-web';
import { renderDocument, sitemap } from 'swiftui-for-web/server';

const pages = {
  '/': () => VStack(Text('Home')).navigationTitle('Trail Guide'),
  '/about': () => VStack(Text('About us')).navigationTitle('About · Trail Guide'),
};

await mkdir('public/about', { recursive: true });
for (const [path, page] of Object.entries(pages)) {
  const html = renderDocument(WindowGroup(page), {
    stylesheets: ['/styles/index.css'],
    scripts: ['/main.js'],
  });
  await writeFile(`public${path === '/' ? '' : path}/index.html`, html);
}
await writeFile('public/sitemap.xml', sitemap(Object.keys(pages), { baseURL: 'https://example.com' }));

Examples/AppleSampleCodeProof renders a real AppleSampleCode.com page this way and tests it against that site’s own renderer: metadata, JSON-LD, headings, links, landmarks, lists, tables and all visible words match.
